## 2. 토론 & 피드백 질문 (팀별 작성)

> 각 질문에 팀의 생각을 자유롭게 적고, 다른 팀/강사와 논의합니다.

### Q1. 브랜치 전략 — 요구사항을 분리해서 개발했나요?
- 요구사항 #2와 #3을 각각 다른 feature 브랜치로 나눠 작업했나요?
- 브랜치를 나눠서 좋았던 점 / 어려웠던 점은?
---
| ✍️ 작성란 |
|-----------|
| 요구사항과 역할 단위로 브랜치를 나눴습니다. 이름은 `feature/req{번호}-{역할}-{기능}` 형식으로 통일해서(예: `feature/req2-fe-devices`, `feature/req2-be-devices-api`), 브랜치 목록만 보고도 어떤 요구사항의 누구 작업인지 알 수 있었습니다. |
| **좋았던 점:** BE가 API를 구현하는 동안 FE가 기다리지 않고 #1 브랜치 위에서 #2 화면 작업을 먼저 진행할 수 있었습니다. 작업이 병렬로 진행돼 대기 시간이 줄었습니다. |
| **어려웠던 점:** 선행 작업이 merge되기 전에 다음 브랜치를 어디서 따야 하는지(main vs 이전 feature 브랜치) 판단이 필요했습니다. 또 #2 merge 후 발견한 작은 버그(필드명 불일치)를 main에 직접 push해서 고쳤는데, 리뷰와 CI를 거치지 않는 경로라는 점에서 fix 브랜치 + PR로 처리하는 게 맞았다고 생각합니다. |
<br>

### Q2. 수동 CI vs 자동 CI — 무엇이 다른가요?
- 요구사항 #1에서 한 "로컬에서 직접 확인(수동 CI)"과
  요구사항 #3의 "GitHub Actions 자동 CI"의 차이는?
- 자동화로 무엇이 좋아졌나요? (사람의 실수, 반복 작업 관점)
---
| ✍️ 작성란 |
|-----------|
| 수동 CI는 각자 로컬에서 서버를 띄우고 curl·브라우저로 확인하는 방식이라, 결과가 개인 환경에 따라 달라졌습니다. 실제로 BE 팀원 로컬에서는 FastAPI 버전 문제가 났고, TE 테스트에서는 대시보드 페이지가 500을 냈지만 FE 로컬 브라우저에서는 정상 동작했습니다. |
| 자동 CI는 매번 깨끗한 동일 환경(Python 3.11 + `requirements.txt`)에서 서버 기동과 API 테스트를 실행하므로, "내 PC에서는 되는데" 문제를 줄이고 기준 환경을 하나로 맞출 수 있습니다. 또 push/PR마다 자동으로 돌아가서 확인을 빼먹는 실수와 반복 작업이 사라집니다. |
<br>

---

### Q3. 수동 배포 vs 자동 CD(Render) — 어떤 차이를 느꼈나요?
- push만 했는데 자동 배포되는 경험은 어땠나요?
- 수동으로 서버에 올리는 것과 비교했을 때 장단점은?
---
| ✍️ 작성란 |
|-----------|
| (참고) 장점은 배포 절차가 사라져 main 반영과 서비스 반영 사이의 시간이 짧아진다는 것입니다. 단점은 **main에 들어간 것이 곧바로 배포된다**는 점입니다. 이번에 main에 직접 push한 수정도 Auto-Deploy가 켜져 있었다면 검증 없이 배포됐을 것이므로, 자동 CD일수록 main 보호(PR 필수, CI 통과 후 배포 등)가 중요하다고 느꼈습니다. |
<br>

---

### Q4. PR / 코드 리뷰 / 충돌 해결에서 배운 점은?
- 같은 파일(`app.js`)을 여러 명이 수정했을 때 충돌이 어떻게 발생했나요?
- 협업 과정에서 팀이 정한 규칙이 있었나요?
---
| ✍️ 작성란 |
|-----------|
| 이번에는 merge 충돌이 발생하지 않았습니다. 역할별로 수정 파일이 나뉘어 있었고(FE는 `app/static/app.js`, BE는 `app/api/*.py`), #3 브랜치를 #2가 merge된 최신 main에서 생성했기 때문입니다. 새 브랜치를 만들기 전에 항상 `git pull`로 main을 최신화한 것이 충돌 예방에 효과적이었습니다. |
| **팀 규칙:** 브랜치 이름 `feature/req{번호}-{역할}-{기능}`, 커밋 메시지 `feat(FE): ...`처럼 타입과 역할을 명시, merge 전 TE 검증 후 PM이 merge. |
| **배운 점:** FE·BE 사이의 **API 응답 필드명 합의**가 중요했습니다. FE가 `lastUsed`로 읽었는데 실제 데이터는 `lastUsedAt`이라 화면에 값이 표시되지 않았습니다. 코드 충돌은 아니지만 인터페이스 불일치라는 협업 문제였고, 작업 전에 응답 예시(JSON)를 먼저 공유했다면 막을 수 있었습니다. |
<br>

### Q5. TE의 수동 검증 Report vs 자동 테스트 스크립트 — 역할 차이는?
- 사람이 시나리오대로 확인하는 것과 스크립트가 자동 검증하는 것,
  각각 언제 더 유용할까요?
---
| ✍️ 작성란 |
|-----------|
| **자동 테스트 스크립트**는 반복 가능하고 환경 차이를 드러내는 데 유용했습니다. #1 Report에서 스크립트가 대시보드 페이지의 500 에러(TE-2 FAIL)를 잡아냈는데, 브라우저로만 확인했다면 놓쳤을 문제입니다. |
| **사람의 수동 검증**은 화면에 실제로 어떻게 보이는지를 확인할 때 유용했습니다. Last Used가 `-`로 표시되는 문제나 badge 색상이 매핑대로 나오는지는 눈으로 보고 발견했습니다. |
| 정리하면, 스크립트는 회귀 검증과 API·상태 코드처럼 명확한 기준이 있는 항목에, 사람은 UI·사용성처럼 판단이 필요한 항목에 강점이 있습니다. 【TE 보완】 |
<br>
